# M2 — Per-party shard persistence (`sovra-state`)

## Context

M1 built the crypto seam: `SilenceBackend::dkg()` returns a `DkgResult { shares: Vec<KeyShare>, address }`
(two opaque shards, sorted by `party_id`) and `sign(signing_hash, shares)` produces `(r, s, y_parity)`
that `sovra_eth::finalize` accepts. But those shards live only in memory — a DKG result is lost the moment
the process ends. M3's endpoints (`POST /v1/signers` to provision, then a later `POST /v1/sign`) need to
**provision once and sign later**, so the shards must survive on disk between calls. M2 builds exactly that
persistence seam, and nothing else: no HTTP, no MPC, no networking.

### The deployment constraint that shapes the design

The two shards are **never co-located**. In production one lives on a **Raspberry Pi**, the other on a
**phone/cloud** host. That is the whole point of 2-of-2 MPC: a single shard at rest is useless — an
attacker needs *both* machines' shards to move funds.

So `sovra-state` models **one party's** local storage: it holds exactly **one** shard per signer plus the
signer metadata. The in-process PoC instantiates **two** stores (one root per party) and saves
`dkg.shares[0]` to one and `dkg.shares[1]` to the other. At M4, when the two cosigners split into two real
processes, each just points its store at its own local directory — a config change, **not** a redesign.

### What exploration confirmed

- **`sovra-types` already has everything needed** (not a stub): `SignerId(pub String)` with
  `new`/`as_str`, `KeyShare(pub Vec<u8>)` with `as_bytes()` / `From<Vec<u8>>`, and
  `SignerMetadata { signer_id, address }`. All three already derive `Serialize`/`Deserialize`, and
  `alloy-primitives` is pulled in **with the `serde` feature**, so `Address` serializes as a hex string.
  M2 reuses these as-is — no new shared types.
- **`sovra-state` is an empty crate.** `Cargo.toml` already declares `sovra-types`, `alloy-primitives`,
  `serde_json`, and dev-dep `tempfile`; `src/lib.rs` is empty. All M2 code lands here.
- **`DkgResult.shares`** (`crates/sovra-mpc/src/types.rs`) is a `Vec<KeyShare>` of the two party shards,
  sorted by `party_id` (index 0 = party 0, index 1 = party 1). This is what gets split across the two
  stores.
- **The shard bytes are `Keyshare::as_slice()`**, reloadable at sign time via `Keyshare::from_bytes`.
  `sovra-state` keeps them **opaque** — it never depends on `sl-dkls23` or `sovra-mpc`.

## Decisions (settled)

1. **Per-party store, PoC runs two.** `SignerStore` = one party's local dir holding one shard per signer.
   Directly reusable at M4 by re-rooting each cosigner's store.
2. **Address lookup included now.** `find_by_address(&Address)` scans `metadata.json` files so M3's sign
   path (keyed off the `from` address that `prepare` already carries) is unblocked.
3. **Filesystem-perms security model now.** On unix, chmod the signer dir `0700` and the files `0600` so
   shard secrecy rests on OS permissions.
4. **At-rest encryption via a `ShardSealer` seam, default passthrough.** Only the shard is secret —
   metadata (the address) is public and stays plaintext. `save_shard` routes shard bytes through
   `ShardSealer::seal` before writing; `load_shard` through `::open` after reading. M2 ships only the no-op
   `Passthrough` sealer: no fake crypto, no crypto dependency, and no performance cost — sealing happens
   **once at load**, before the MPC protocol starts, not per round. At M4/deploy a real sealer drops in
   (KMS/HSM on the cloud side, TPM/secure-element or an Argon2id passphrase on the Pi) with **zero change
   to `SignerStore`'s public API**.
5. **`sovra-state` stays backend-agnostic and dependency-minimal.** It stores opaque `KeyShare` bytes and
   does **not** depend on `sovra-mpc`/`DkgResult`. The "split a `DkgResult` across two stores" wiring
   belongs to the M3 orchestrator.

## Data flow (M2 in one picture)

```
DkgResult{ shares: [KeyShare_0, KeyShare_1], address }        (from M1's backend.dkg)
                 |                    |
   store_p0.save_shard(meta, &shares[0])   store_p1.save_shard(meta, &shares[1])
   (Pi root)             |                 |            (phone/cloud root)
     <root_p0>/<id>/{metadata.json, shard.bin}   <root_p1>/<id>/{metadata.json, shard.bin}
                 |                    |
   store_p0.load_shard(id) --------> [ &shares back, byte-identical ] <-- store_p1.load_shard(id)
                 |
   store.find_by_address(from) -> SignerId          (M3 signs keyed off `from`)
```

## Layout on disk (per store root)

```
<root>/                     # one party's dir (e.g. the Pi's, or the phone's)
  <signer_id>/              # dir 0700
    metadata.json           # SignerMetadata { signer_id, address }   (0600)
    shard.bin               # this party's single (sealed) shard      (0600)
```

Both parties write identical `metadata.json` (both need the address); each writes only its own `shard.bin`.

## Files to create/modify

### 1. `crates/sovra-state/Cargo.toml`
Add `thiserror = { workspace = true }` (already a workspace dependency). Existing deps stay: `sovra-types`,
`alloy-primitives`, `serde_json`; dev-dep `tempfile`.

### 2. `crates/sovra-state/src/lib.rs` — the whole milestone

**Error type** (matching the crate's `XxxError` convention, cf. `PrepareError`/`FinalizeError`):
```rust
#[derive(thiserror::Error, Debug)]
pub enum StateError {
    #[error("i/o error at {path}: {source}")]
    Io { path: PathBuf, #[source] source: std::io::Error },
    #[error("serialization error")]
    Serde(#[from] serde_json::Error),
    #[error("signer not found: {0}")]
    NotFound(SignerId),
    #[error("no signer found for address {0}")]
    AddressNotFound(Address),
    #[error("could not unseal shard")]
    Seal,
}
```

**`ShardSealer`** — the at-rest encryption seam (only shard bytes pass through it):
```rust
pub trait ShardSealer: Send + Sync {
    fn seal(&self, plaintext: &[u8]) -> Result<Vec<u8>, StateError>;
    fn open(&self, sealed: &[u8]) -> Result<Vec<u8>, StateError>;
}

/// M2 default: identity. Real KMS/TPM/passphrase sealers land at M4.
pub struct Passthrough;
```

**`SignerStore`** — one party's store rooted at a directory, holding a sealer:
```rust
pub struct SignerStore { root: PathBuf, sealer: Box<dyn ShardSealer> }

impl SignerStore {
    /// Open (creating if needed) a store rooted at `root`, using `Passthrough`.
    pub fn open(root: impl Into<PathBuf>) -> Result<Self, StateError>;

    /// Same, with a custom at-rest sealer (M4: KMS/TPM/passphrase).
    pub fn open_with_sealer(root: impl Into<PathBuf>, sealer: Box<dyn ShardSealer>)
        -> Result<Self, StateError>;

    /// Persist this party's single shard + the signer metadata (idempotent).
    pub fn save_shard(&self, meta: &SignerMetadata, shard: &KeyShare) -> Result<(), StateError>;

    /// Load this party's shard for a signer.
    pub fn load_shard(&self, id: &SignerId) -> Result<KeyShare, StateError>;

    /// Load a signer's metadata.
    pub fn load_metadata(&self, id: &SignerId) -> Result<SignerMetadata, StateError>;

    /// Signer id whose metadata.address matches (scans metadata.json files).
    pub fn find_by_address(&self, address: &Address) -> Result<SignerId, StateError>;
}
```

Implementation notes:
- Reuse `SignerId`, `KeyShare`, `SignerMetadata` from `sovra-types`. No new shared types.
- Metadata via `serde_json::to_vec_pretty` / `from_slice`; **not** sealed.
- Shard: `save_shard` writes `sealer.seal(shard.as_bytes())`; `load_shard` returns
  `KeyShare::from(sealer.open(&raw)?)`. With `Passthrough` this is byte-for-byte identity.
- **Atomic writes:** write to a temp file in the signer dir, then `fs::rename` into place, so an
  interrupted save never leaves a half-written shard/metadata.
- **Permissions (`#[cfg(unix)]`):** signer dir `0700`, `shard.bin`/`metadata.json` `0600` via
  `std::os::unix::fs::PermissionsExt`. No-op on non-unix.
- `NotFound` when the signer dir / `shard.bin` is absent; wrap raw `io::Error` as `Io { path }`.
- `find_by_address`: read each child dir's `metadata.json`, compare `address`, first match wins else
  `AddressNotFound`. Fine for the PoC's handful of signers.
- **Watch-point:** `signer_id` becomes a directory name — guard against path separators / `..` so a bad id
  can't escape the store root.

## The M2 tests (in `sovra-state`, using `tempfile`)

1. **Round-trip:** save then assert `load_shard == shard` and `load_metadata == meta`.
2. **Two-party (the deployment shape):** two stores at two roots; save shard-0 to one and shard-1 to the
   other for the same `SignerId`; each loads back its own shard and they differ.
3. **Address lookup:** `find_by_address(meta.address) == signer_id`; unknown address → `AddressNotFound`.
4. **Not found:** `load_shard`/`load_metadata` for an unknown `SignerId` → `NotFound`.
5. **Permissions (`#[cfg(unix)]`):** `shard.bin` mode is `0600` after save.
6. **Sealer seam:** with a toy invertible sealer (byte-reverse/XOR), `save`→`load` still returns the
   original shard, and the on-disk `shard.bin` differs from the raw bytes — proving `seal`/`open` are
   wired through.

Green tests == M2 done: a signer's two shards persist to two independent per-party roots, reload

the persistence seam that M3's `POST /v1/signers` + `POST /v1/sign` build on unchanged.
